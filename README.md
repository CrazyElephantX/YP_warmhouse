# Задание 1. Анализ и планирование

## 1. Описание функциональности монолитного приложения

### 1.1 Управление отоплением
- Пользователи могут удалённо включать и выключать отопление в своих домах через веб-интерфейс
- Система управляет отоплением каждого дома независимо
- Требует специалиста для первоначального подключения датчика к системе
- Синхронное взаимодействие: сервер инициирует запрос к датчику, ожидает ответа

### 1.2 Мониторинг температуры
- Система получает данные о текущей температуре с датчиков отопления, установленных в домах
- Пользователи просматривают показания температуры через веб-интерфейс
- Данные получаются по инициативе сервера
- Синхронная архитектура: сервер опрашивает датчики последовательно

## 3. Определение доменов и границы контекстов
### **1. Device Management (Управление устройствами)**
- **Ответственность**: Регистрация, конфигурирование и жизненный цикл всех умных устройств в системе
- **Ключевые операции**:
  - Регистрация нового устройства
  - Конфигурирование параметров устройства
  - Получение списка доступных устройств пользователя
  - Удаление устройства
  - Управление состоянием подключения

### **2. Heating Management (Управление отоплением)**
- **Ответственность**: Управление системой отопления дома, включение/выключение, установка температуры
- **Ключевые операции**:
  - Включение/выключение отопления
  - Установка целевой температуры
  - Получение текущей температуры

## **4. Проблемы монолитного решения**

**Недостатки текущей архитектуры:**
- **Масштабируемость**: Невозможно масштабировать отдельные функции независимо. Если требуется большая пропускная способность для мониторинга температуры, нужно масштабировать весь монолит
- **Развёртывание**: Любое обновление функции требует перезагрузки всей системы, включая стабильные компоненты
- **Надёжность**: Ошибка в одном модуле может привести к сбою всей системы
- **Сложность технологического долга**: Со временем монолит становится всё сложнее для модификации
- **Командные границы**: Разработка усложняется по мере роста команды, так как все работают с одной кодовой базой
- **Синхронизм**: Все операции синхронные, что ограничивает отзывчивость системы и её способность обрабатывать несинхронные события (например, push-уведомления от датчиков)

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры
